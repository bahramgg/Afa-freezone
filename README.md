# AFA — درگاه پرداخت ارزی منطقه آزاد

سامانهٔ دریافت، ارسال و تسویهٔ وجوه ارزی برای بازرگانان منطقه آزاد، با پرداخت
روی شبکهٔ BSC و تسویهٔ ریالی از طریق بانک عامل.

## Stack

Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 · Prisma 7 +
PostgreSQL · viem (BSC) · Zustand · Radix UI · Recharts

## چهار درگاه

| ------------ | -------------- | ------------------------------------------------- |
| `/`          | لندینگ عمومی   | ورود به هر چهار پنل                               |
| `/dashboard` | بازرگان ایرانی | صدور فاکتور، درخواست ارسال، درخواست تسویه، والت‌ها |
| `/foreign`   | بازرگان خارجی  | پرداخت فاکتور، تأیید درخواست دریافت                |
| `/admin`     | ادمین سازمان   | احراز هویت، تأیید تراکنش‌ها، گزارش، تنظیمات        |
| `/bank`      | بانک عامل      | قفل نرخ، کیف پول‌ها، ثبت تراکنش، تسویهٔ ریالی      |

## راه‌اندازی

```bash
# ۱) وابستگی‌ها
npm install

# ۲) پیکربندی — .env.example را کپی و مقادیر را پر کنید
cp .env.example .env

# ۳) دیتابیس
npm run db:migrate      # ساخت جدول‌ها
npm run db:seed         # ساخت حساب ادمین و بانک + کیف پول‌های بانک

# ۴) بررسی اتصال زنجیره (اختیاری ولی توصیه‌شده)
npm run check:chain

# ۵) اجرا
npm run dev
```

### متغیرهای الزامی

| متغیر                      | توضیح                                                        |
| -------------------------- | ------------------------------------------------------------ |
| `DATABASE_URL`             | رشتهٔ اتصال PostgreSQL                                       |
| `AUTH_SECRET`              | حداقل ۳۲ کاراکتر — `openssl rand -base64 48`                 |
| `SEED_ADMIN_PASSWORD`      | رمز اولین حساب ادمین (فقط هنگام seed)                        |
| `SEED_BANK_PASSWORD`       | رمز اولین حساب بانک (فقط هنگام seed)                         |
| `CHAIN_RPC_URL`            | نقطهٔ RPC کلیددار (QuickNode، Alchemy، NodeReal، …)           |
| `SEED_BANK_RECEIVE_WALLET` | بدون آن هیچ فاکتوری قابل تأیید نیست — آدرسی برای پرداخت ندارد |

بقیهٔ متغیرها پیش‌فرض دارند و در `.env.example` توضیح داده شده‌اند.

## شبکه

هیچ‌چیز در کد به یک زنجیرهٔ خاص گره نخورده است: نام شبکه، سکهٔ کارمزد و نشانی
کاوشگر همه از پیکربندی خوانده می‌شوند. جابه‌جایی بین زنجیره‌ها یعنی تغییر
`.env` به‌علاوهٔ استقرار دوبارهٔ کارخانهٔ تسویه — چون نشانی‌های واریز از روی آن
مشتق می‌شوند و به همان زنجیره تعلق دارند و نه هیچ زنجیرهٔ دیگری.

| | |
|---|---|
| `11155111` | **اتریوم سپولیا** — هدف فعلی راه‌اندازی |
| `56` | زنجیرهٔ هوشمند بایننس |
| `1` | اتریوم |
| `31337` | نود محلی (`npx hardhat node`) |

### راه‌اندازی روی سپولیا

سپولیا USDT ندارد، پس یک توکن جایگزین مستقر می‌شود. اسکریپت آن روی هر زنجیرهٔ
واقعی از کار سر باز می‌زند: چیزی که مستقر می‌کند پول بازی است و هرکسی می‌تواند
از آن ضرب کند.

```bash
# ۱) کلید مستقرکننده را از فاوست سپولیا شارژ کنید (چند صدم ETH کافی است).
#    این کلید هرگز وارد محیط برنامه نمی‌شود — فقط روی خط فرمان.

# ۲) توکن آزمایشی
DEPLOY_PRIVATE_KEY=0x… npm run contracts:token
#    نشانی چاپ‌شده را در USDT_CONTRACT_ADDRESS بگذارید

# ۳) کارخانهٔ تسویه، روی همان توکن
DEPLOY_PRIVATE_KEY=0x… npm run contracts:deploy
#    نشانی چاپ‌شده را در GATEWAY_FACTORY_ADDRESS بگذارید

# ۴) بررسی اتصال، سپس دیتابیس
npm run check:chain
npm run db:migrate && npm run db:seed
```

`USDT_DECIMALS=6` روی سپولیا درست است — USDT هرجا که اهمیت دارد شش رقم اعشار
دارد، نه هجده. این عدد در دفترکل هم می‌نشیند، پس تغییر آن روی سامانه‌ای که
تراکنش ثبت کرده دفتر را بی‌معنا می‌کند؛ قبل از اولین پرداخت تعیینش کنید.

نقطهٔ عمومی `https://ethereum-sepolia-rpc.publicnode.com` برای سپولیا کافی است:
تگ `finalized` را سرو می‌کند و بازهٔ `eth_getLogs` تا حدود هزار بلوک را با فیلتر
نشانی می‌پذیرد (`CHAIN_SCAN_BATCH=500`). روی BSC اما **RPC کلیددار الزامی است**؛
نقاط عمومی آنجا `eth_getLogs` را محدود یا مسدود می‌کنند و سقف بازهٔ هر درخواست
به پلن بستگی دارد (Alchemy رایگان: ۱۰ بلوک، QuickNode رایگان: ۵ بلوک).

### قطعیت تراکنش

`CHAIN_FINALITY="finalized"` یعنی سامانه بلوک نهایی‌شده را از نود می‌پرسد. این
معیار از شمارش تأییدیه بهتر است: بلوک نهایی‌شده برگشت‌ناپذیر است، در حالی که روی
BSC «۱۵ تأییدیه» فقط هفت ثانیه محافظت است و روی اتریوم عدد امن به روزش بستگی
دارد. هم BSC و هم هر شبکهٔ اتریومی پس از merge — از جمله سپولیا — این تگ را سرو
می‌کنند. برای نودی که سرو نمی‌کند، `CHAIN_FINALITY="confirmations"` به شمارش
بلوک برمی‌گردد.

### رصدگر واریزی

دو حالت دارد. **حالت توصیه‌شده** یک پروسهٔ دائم است که با WebSocket به انتقال‌های
مقصدِ کیف پول‌های درگاه گوش می‌دهد و بی‌درنگ واکنش نشان می‌دهد:

```bash
npm run watch:chain
```

زیر آن هر ۲۰ ثانیه یک sweep هم اجرا می‌شود تا شکاف ناشی از قطعی سوکت را ببندد و
واریزی‌ها را پس از نهایی‌شدن ارتقا دهد.

**حالت جایگزین** برای محیط‌هایی که پروسهٔ دائم ندارند، نقطهٔ پایانی زمان‌بند است:

```bash
* * * * * curl -fsS -X POST https://<host>/api/chain/watch \
  -H "Authorization: Bearer $CHAIN_WATCHER_TOKEN" >/dev/null
```

> روی سپولیا با بلوک دوازده‌ثانیه‌ای، پیمایش HTTP به‌تنهایی هم جا می‌افتد؛
> روی زنجیره‌ای با بلوک نیم‌ثانیه‌ای ممکن است از سرِ زنجیره عقب بماند. اگر رصدگر در دسترس نباشد سامانه همچنان کامل کار می‌کند: پرداخت‌ها با
> ثبت دستی هش تأیید می‌شوند و همان راستی‌آزمایی روی زنجیره اعمال می‌گردد.

## امنیت

- **هیچ کلید خصوصی‌ای در سامانه نگهداری نمی‌شود.** اپراتور بانک انتقال را بیرون
  از سامانه امضا می‌کند و فقط هش را ثبت می‌کند؛ سامانه مبلغ، گیرنده و موفقیت
  تراکنش را مستقیماً از زنجیره می‌خواند.
- ورود بازرگان داخلی با **کد یک‌بارمصرف ایمیلی** است؛ بازرگان خارجی و کارکنان با
  رمز عبور وارد می‌شوند. رمزها و کدها با Argon2id هش می‌شوند. نشست‌ها توکن
  تصادفی‌اند و فقط خلاصهٔ SHA-256 آن‌ها ذخیره می‌شود.
- هر انتقال وضعیت، هم نقش فراخوان و هم وضعیت فعلی رکورد را سمت سرور بررسی
  می‌کند؛ یک کلاینت کهنه نمی‌تواند مرحله‌ای را تکرار یا رد کند.
- دامنهٔ دادهٔ هر کوئری از نشست استخراج می‌شود، نه از پارامتر کلاینت.
- هر تغییر وضعیت در `StatusEvent` با عامل، زمان و دلیل ثبت می‌شود.

### ایمیل

`EMAIL_FROM` باید روی دامنه‌ای باشد که نزد ارائه‌دهنده **تأیید شده** است، وگرنه
ارسال رد می‌شود. برای Resend دامنه را در <https://resend.com/domains> اضافه و
تأیید کنید.

## راهنمای کارکرد

برای هر پنل یک ویدئوی راهنما و یک سند PDF ساخته می‌شود و در صفحهٔ نخست سایت
عرضه می‌گردد. مخاطب این‌ها کاربر سامانه نیست؛ کسی است که می‌خواهد پیش از ورود
بفهمد سامانه چه می‌کند — مسئول سازمان، حسابرس، یا همکار تازه.

ویدئوها **صدا ندارند**؛ همهٔ توضیحات روی تصویر نوشته شده، پس در یک جلسه با صدای
خاموش هم کار می‌کنند و می‌شود روی هر مرحله نگهشان داشت.

```bash
npm run guides                # هر چهار پنل: ویدئو و سند
npm run guides -- bank        # فقط یک پنل
npm run guides -- --pdf       # فقط سندها، که سریع است
```

متن راهنماها در `scripts/media/content.ts` است. **وقتی رفتار سامانه عوض می‌شود،
این فایل هم باید عوض شود** — وگرنه راهنما چیزی را توضیح می‌دهد که دیگر وجود
ندارد. خروجی در `public/guide/` قرار می‌گیرد و کامیت می‌شود، چون همان چیزی است
که سایت سِرو می‌کند.

ساخت ویدئو به `ffmpeg` نیاز دارد؛ مسیر آن را در `FFMPEG_PATH` بگذارید. ساخت سند
فقط به Chromium نیاز دارد (`CHROMIUM_PATH`، پیش‌فرض `/opt/pw-browsers/chromium`).

## آزمون

آزمون‌ها سرتاسری‌اند: همان مسیرهایی را صدا می‌زنند که پنل‌ها صدا می‌زنند، روی
دیتابیس واقعی و زنجیرهٔ واقعی. چیزی شبیه‌سازی نشده — چون آنچه بیش از همه ارزش
بررسی دارد (چه کسی اجازهٔ تغییر وضعیت دارد، قرارداد دقیقاً چقدر پرداخت می‌کند،
دفترها با زنجیره می‌خوانند یا نه) دقیقاً همان چیزی است که یک شبیه‌ساز به‌جای ما
تصمیم می‌گیرد.

```bash
npm test                 # هرچه پیش‌نیازش برقرار است
npm test -- import       # فقط آزمون‌های منطبق
npm test -- --list       # فهرست آزمون‌ها
```

پیش از اجرا باید دیتابیس، سرور توسعه، و برای آزمون‌های زنجیره یک نود محلی
(`npx hardhat node` و سپس `npm run chain:local`) در دسترس باشند. `npm test` هر
چهار پیش‌نیاز را می‌سنجد و آنچه را برقرار نیست صریح می‌گوید؛ آزمونی که اجرا نشود
گزارش می‌شود، نه اینکه بی‌صدا کنار گذاشته شود. جزئیات در `tests/README.md`.

> برای اجرای آزمون `EMAIL_PROVIDER=console` بگذارید. هر ورود یک ایمیل است و یک
> اجرای کامل ده‌ها ورود دارد؛ با ارائه‌دهندهٔ واقعی این یعنی هزینه و خدشه به
> اعتبار دامنهٔ ارسال، آن هم برای نشانی‌هایی که کسی نمی‌خواند.
